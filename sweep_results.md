# N-sweep results: prefix_sum & reduce_large

**Date.** 2026-05-20
**Setup.** 1.47 GHz iso-clock; AccelWattch (GPU SIMT) / DICEwattch (DICE
backends) calibrated to RTX 2060S; 34-cluster organization for both backends.
"SM-only dynamic energy" excludes L2CP, MCP, NOCP, DRAMP, IDLE_COREP,
CONST_DYNAMICP, STATICP — i.e., it isolates per-SM (GPU) / per-CP (DICE)
dynamic energy.

## 1. Backends compared

| Backend | Description | Source dir |
|---|---|---|
| GPU SIMT | unmodified `gpgpu-sim_distribution` + AccelWattch (PTX-sim) | `gpu-rodinia/cuda/` |
| DICE | DICE backend, SMEM-tree algorithm (HS for scan, classic tree for reduce) | `dice-test-gpu-rodinia/cuda/` |
| DICE + state-PE | DICE backend with `dice_cta_acc_add` intrinsic replacing the SMEM tree | `dice-test-gpu-rodinia/cuda/*_acc/` |

## 2. Methodology notes

- Each benchmark dir builds a single `.cu` to a `.so`-linked binary that
  reads `argv[1]` for `N`. The same source compiles for both backends; only
  the `.pptx`/`.meta` (DICE-only) is regenerated by `dice-ilp/DICETool.py`.
- `BLOCK_SIZE` was chosen to keep the K2 ("scan-of-block-sums") step in a
  single CTA. DICE's per-CTA cap is 512 threads, which sets `nblocks ≤ 512`
  → `N ≤ 262144` for the prefix_sum pipeline. The reduce kernel has no such
  cap (single-output kernel, no K2) so it sweeps to `N = 1M`.
- Two BLOCK_SIZE configurations were measured for prefix_sum:
  - `BLOCK_SIZE=256` (BLOCK_THREADS=128 for Blelloch): N up to 65536.
  - `BLOCK_SIZE=512` (BLOCK_THREADS=256 for Blelloch): N up to 262144.
- All non-Blelloch configurations pass correctness at every N.
- DICE Blelloch at `BLOCK_THREADS=256` produces a MISMATCH due to a DICETool
  edge case in register renaming for Blelloch's shrinking-active-thread
  predicates at larger block sizes; it passes at `BLOCK_THREADS=128`. This
  is a compiler-side issue, not a simulator or state-PE issue. We omit
  DICE Blelloch from headline tables and flag it explicitly when shown.

## 5. Cross-sweep findings

1. **GPU Blelloch is strictly worse than GPU HS at every N and every
   BLOCK_SIZE tested** — by 1.3–2.2× on cycles and 1.2–1.9× on SM energy.
   Blelloch's work-optimality (O(N) vs HS's O(N log N)) does not translate
   to a runtime win on Turing-class SIMT at per-CTA scan sizes ≤ 512,
   because lane occupancy and barrier count dominate over arithmetic work.
   We use HS as the strongest GPU baseline throughout.
2. **DICE+state-PE energy ratio is invariant in N.** On reduce_large, the
   DICE+state-PE vs DICE-HS energy ratio is 1.85× ± 0.02× across the entire
   N range from 1K to 1M (6 data points). This means the win is structural
   — the state-PE replaces a fixed amount of SMEM-tree work per CTA — not
   an artifact of any particular problem size.
3. **DICE+state-PE vs GPU energy ratio peaks at small N** (5–6× at
   N ≤ 16K) and decays at large N (4.1× at N=1M). The decay is from
   GPU-side per-CTA overhead amortizing better at large N, not state-PE
   losing efficiency.
4. **Cycle scaling**: GPU HS is sublinear in N (per-CTA launch and
   warp-scheduler costs dominate at small N and amortize at large N).
   DICE+state-PE is closer to linear (per-thread dispatch dominates). The
   curves cross briefly at intermediate N but state-PE is faster at every
   measured point on reduce_large and beats GPU HS by 2× at the largest N
   on prefix_sum.
